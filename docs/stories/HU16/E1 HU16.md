# Documento Técnico: Módulo ML de Detección de Fraude y Scoring (ScoreLeads)

**Proyecto:** Ruta Hogar - Plataforma de Precalificación Financiera Inmobiliaria
**Stack ML:** Python, FastAPI, XGBoost, SHAP
**Objetivo:** Implementar un sistema automatizado que detecte leads presuntamente fraudulentos o inconsistentes, indicando los motivos exactos de la alerta, con capacidad de aprendizaje continuo basado en la retroalimentación de los administradores.

---

## 1. Arquitectura Algorítmica y Justificación

El motor de detección de fraude y precalificación se construirá utilizando un modelo de **Gradient Boosting basado en árboles (XGBoost)**, complementado con **TreeSHAP** para la explicabilidad. Se descartan modelos de Deep Learning o Redes Neuronales de Grafos (GNN) debido a la naturaleza del negocio.

### Justificación Técnica de XGBoost:
*   **Manejo de Filtros No Compensatorios:** XGBoost particiona los datos mediante reglas lógicas secuenciales. Esto permite modelar filtros estrictos (ej. si el nivel de morosidad es crítico, no importa cuán alto sea el ingreso, el lead es riesgoso), imitando la lógica de riesgo de una inmobiliaria o banco.
*   **Resiliencia ante Datos Faltantes (Missing Values):** En los formularios de captación, los usuarios suelen omitir datos no obligatorios. XGBoost maneja valores nulos (`NaN`) nativamente, aprendiendo la dirección estadística óptima sin requerir imputaciones artificiales que distorsionen el perfil del lead.
*   **Explicabilidad Legal (SHAP):** La Ley 21.719 exige transparencia. *TreeSHAP* permite calcular en milisegundos cuánto contribuyó cada variable al puntaje de riesgo. El sistema no será una "caja negra"; entregará el puntaje y los motivos (ej. "Carga financiera excede límite: +30% riesgo").
*   **Eficiencia en Datos Tabulares:** Para variables financieras puramente numéricas y categóricas, los algoritmos basados en árboles superan en precisión y velocidad de inferencia a arquitecturas más complejas.

## 2. Plan de Diseño y Flujo de Aprendizaje (Human-in-the-Loop)

El sistema operará bajo un modelo de aprendizaje supervisado con intervención humana (HITL), donde el Ejecutivo Comercial reporta, el Admin Inmobiliario bloquea/reactiva, y el modelo aprende asimétricamente de estas acciones.

### Manejo Asimétrico de Errores (Cost-Sensitive Learning)
Para asegurar que el modelo mejore sin descalibrarse fuertemente por falsos positivos, el reentrenamiento automatizado asignará pesos distintos (*Sample Weights*) a la retroalimentación:
*   **Bloqueo Confirmado (True Positive):** Si el sistema marca un fraude y el Admin lo bloquea efectivamente, el registro entra al reentrenamiento con un peso estándar ($w = 1.0$). El modelo refuerza este patrón.
*   **Reactivación / Falsa Alarma (False Positive):** Si el sistema marca fraude pero el Admin lo revisa y lo reactiva (validando que el lead es legítimo), este registro se inserta con un peso estadístico menor (ej. $w = 0.3$). Esto suaviza la frontera de decisión para no penalizar severamente el aprendizaje, enseñándole al modelo que existen excepciones a reglas rígidas.

### Pipeline de Reentrenamiento
Un trabajo programado (Cron Job) mensual extraerá los nuevos reportes y resoluciones desde Supabase. Entrenará un modelo candidato y, si mejora la métrica de validación (F1-Score) sin aumentar los falsos positivos, actualizará el archivo del modelo en producción (FastAPI) sin tiempo de inactividad.

## 3. Variables del Modelo (Features)

El modelo consumirá una matriz tabular extraída desde Supabase, anonimizada (sin RUT ni Nombres) para proteger la privacidad.

### A. Variables Financieras Base
*   **Ingreso Líquido Mensual:** Se evalúa la capacidad de pago. Si se usa Open Banking, se calcula la varianza entre lo autodeclarado y lo comprobado. *Por qué:* Discrepancias masivas son el primer indicador de fraude o inflado de perfil.
*   **Carga Financiera (Deuda/Ingreso):** Relación entre las cuotas de deuda mensual (tarjetas, créditos) y el ingreso. *Por qué:* Permite detectar si el usuario miente sobre su capacidad de endeudamiento real para un hipotecario.
*   **Ahorro para el Pie:** Monto disponible y comprobable. *Por qué:* Actúa como un filtro no compensatorio clave; sin pie, la viabilidad comercial es nula.
*   **Historial de Morosidad (CMF/Buró):** Días de atraso en el sistema financiero. *Por qué:* Un historial manchado que el usuario intenta ocultar es una alerta inmediata.

### B. Variables de Comportamiento (Antifraude)
*   **Velocidad de Completado (Time-to-Submit):** Tiempo en segundos desde que carga el formulario hasta el envío. *Por qué:* Tiempos subhumanos (< 3 segundos) indican automatización o bots inyectando leads basura.
*   **Inconsistencia de Geolocalización (IP vs Dirección):** Comparación entre la ubicación de la IP y la comuna de residencia declarada. *Por qué:* Ayuda a detectar granjas de clics o suplantaciones lejanas al área de interés del proyecto inmobiliario.
*   **Historial de Dispositivo/IP (Rate Limiting):** Frecuencia de registros desde la misma IP. *Por qué:* Previene el "fuerza bruta" de leads, donde un usuario intenta múltiples combinaciones de sueldo para ver con cuál obtiene un *score* alto.

---

## 4. Flujo de Ejecución (Endpoint)
1. Frontend envía el `payload` con las variables al endpoint `/api/v1/ml/fraud-scoring`.
2. FastAPI pasa los datos al modelo `.pkl` cargado en memoria.
3. XGBoost calcula la probabilidad de fraude (0 a 100%).
4. SHAP extrae el "Top 3" de variables contribuyentes.
5. El sistema persiste el score en base de datos y emite la alerta al dashboard de administración.
