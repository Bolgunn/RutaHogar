## 3. Arquitectura definitiva aprobada y módulos propuestos

`frontend -> Supabase Storage privado (original temporal)`

`backend/Vercel -> referencia temporal segura -> Azure Document Intelligence (OCR)`

`resultado Azure -> parser por tipo documental -> Pydantic -> normalización -> comparación -> revisión del usuario`

`confirmación -> antecedentes actualizados sin scoring -> borrado original -> datos validados pendientes -> acción explícita de actualización -> nueva evaluación`

Azure recibe temporalmente el documento desde Storage mediante signed URL de corta duración o mecanismo seguro equivalente. La referencia la genera servidor para un objeto ya vinculado a sesión/usuario; no se aceptan URLs arbitrarias del cliente. El binario no atraviesa una Vercel Function. El backend sólo procesa metadatos y resultados JSON/texto/layout acotados; no descarga, decodifica, inspecciona bytes, divide ni rasteriza archivos.

| Componente futuro | Responsabilidad | Frontera aprobada |
| --- | --- | --- |
| Frontend | Selección, consentimiento y carga directa a Storage; revisión/confirmación y acción explícita del score | Sin credenciales Azure, decisión autónoma ni proxy de upload a Vercel. |
| Supabase Storage | Custodia temporal privada y entrega controlada al OCR | Sin bucket público, acceso del ejecutivo ni URLs públicas permanentes. |
| PostgreSQL / `repository.py` + RPC | Metadata, expediente mínimo temporal, decisiones, evidencia y estado durable de orquestación/cleanup | Sin PDF, imagen, base64 ni OCR bruto persistente. |
| Backend `routes.py`, `service.py` | Auth, orquestar envío/consulta Azure, validar contrato y gestionar estados/reintentos | Sin procesamiento de binarios ni OCR; ninguna llamada al score durante confirmación. |
| `storage.py` | Reservar ruta, consultar metadata, generar referencia temporal y solicitar/verificar borrado | No descargar binario a backend; service role no llega a Azure ni al parser. |
| `AzureOcrClient` (nombre propuesto) | Enviar referencia, consultar operación/resultado y solicitar borrado remoto soportado | Azure sólo reconoce texto/layout; no elige valores, escribe en Supabase, calcula score ni asigna estados de respaldo. |
| Parsers por tipo | Interpretar resultado de reconocimiento usando sólo allowlist explícita del tipo | Deterministas, sin LLM, DB ni scoring; ambigüedad produce no detectado/ambiguo. |
| Pydantic, normalización, comparación | Validación estructural/semántica y contraste con declaraciones | El resultado OCR nunca se considera dato financiero confirmado por sí solo. |
| Adaptador HU23/HU13 | Registrar antecedentes confirmados sin cálculo; evaluación posterior por acción del usuario | Sin modificar semántica global de `data_update` ni fórmulas. |

El OCR remoto es asíncrono. Persistir identificación de operación, estado y próximo intento permite reanudar consultas sin mantener una Function abierta ni depender de tareas en memoria. Esto es **orquestación de OCR externo**, no un worker OCR separado. Polling acotado con Retry-After/backoff y cleanup mediante endpoint backend protegido + ejecución programada cada hora inicialmente; no se introduce un runner ni infraestructura extra de OCR.

Alternativas evaluadas y descartadas para la arquitectura seleccionada: worker OCR separado, Tesseract como OCR principal, PyMuPDF para OCR local, `spa.traineddata`, Groq Vision y extracción/rasterización binaria local en Vercel. Se mencionan sólo como antecedentes descartados, no como fallback ni etapas futuras seleccionadas. No se envía el documento ni su OCR a Groq/OpenAI o a otro LLM.

En tests futuros, fake de Azure y fixtures OCR sintéticos sin red. Sin configuración Supabase/Azure, HU23 informa indisponibilidad para documentos reales; no reemplaza silenciosamente el proveedor ni guarda originales/resultados OCR en localStorage/IndexedDB.

## 4. Flujo end-to-end y estados

1. **Reservar:** backend verifica Auth, rol, precalificación propia y consentimiento que informa procesamiento externo Azure; fija revisión base, UUID y vencimiento. Devuelve límites de la configuración única.
2. **Subir:** frontend carga directamente a bucket privado temporal, ruta del servidor, `upsert=false`. Backend recibe sólo JSON de reserva/finalización, nunca el documento. MIME y verificaciones del cliente no son prueba suficiente de contenido real.
3. **Admisión y referencia:** consultar metadata de Storage, verificar dueño/tamaño/límites conocidos y generar signed URL corta sólo para el objeto reservado. El cliente cuenta páginas antes de subir y rechaza PDF >2 páginas; cada imagen cuenta como una página. Es restricción técnica/UX F0, no frontera de seguridad absoluta. Verificación confiable adicional sólo si aparece una opción simple sin binarios Vercel, sin bloquear v1 ni introducir worker OCR (§13).
4. **OCR Azure:** backend solicita reconocimiento externo por referencia y persiste el ID de operación. Azure lee temporalmente el archivo, devuelve texto/layout y no decide valores ni accede a PostgreSQL. PDF digital, scan e imagen siguen esta misma frontera; no fallback local o LLM.
5. **Consultar y parsear:** obtener respuesta acotada de la operación; validar su envoltura y ejecutar sólo el parser del tipo seleccionado. Allowlists cerradas en §2; discrepancia de tipo no habilita otros parsers silenciosamente. Ambigüedad/múltiples candidatos sin regla suficiente → no detectado/ambiguo y revisión del usuario.
6. **Validar/normalizar/comparar:** `parser -> Pydantic -> normalización -> comparación`, con revisión base y versiones fijadas. Conservar sólo candidatos mínimos necesarios para revisión; descartar texto/layout bruto tras uso. Persistir esos datos mínimos y solicitar borrado anticipado del resultado Azure si está soportado; no esperar confirmación para iniciar ese borrado remoto.
7. **Revisar:** mostrar declarado/detectado, cobertura, coincidencias/diferencias e incertidumbre. Casillas sin aceptación implícita. Lo no detectado no se sustituye por cero ni por una elección del backend.
8. **Confirmar:** registrar decisión y actualizar sólo antecedentes aceptados por vía HU23 sin scoring; conservar valores si el usuario así decide. No modificar evaluación previa. Cancelar no cambia declaraciones. Registrar obligación de eliminar original en la misma transacción del cierre.
9. **Eliminar original:** iniciar borrado al confirmar/cancelar/error terminal/abandono; reintentos idempotentes y verificación de ausencia. Abandono: máximo 24 h. Separar estado de borrado Supabase del estado de borrado de resultado Azure; atender operaciones tardías incluso tras cerrar la sesión.
10. **Pendiente de incorporar:** una vez actualizados antecedentes y eliminado el original, quedan datos validados pendientes de incorporación a una evaluación, no un score nuevo ni un archivo a conservar. Si falla el borrado mostrar pendiente; no revertir la confirmación ni marcar falsamente eliminado.
11. **Actualizar score con datos validados:** otra acción explícita del usuario crea una **nueva** evaluación/historial con la declaración vigente; no reutiliza ni modifica la evaluación histórica. La UX presenta primero el borrado y datos pendientes de incorporación; mientras se recupera un `delete_pending`, informa su estado y no calcula automáticamente. La habilitación visual exacta se resuelve al implementar sin cambiar la secuencia aprobada.

Estados técnicos propuestos: `awaiting_upload -> ocr_pending -> ocr_running -> parsing -> awaiting_review -> confirmed | cancelled | failed | expired`. Los nombres no fijan schema. Registrar generación/lease/idempotencia para evitar resultados tardíos; un retry de consulta no equivale a reenviar OCR. Políticas aprobadas: Retry-After, backoff exponencial acotado y máximos finitos configurados; timeout/5xx/429/running se tratan según §8, sin multiplicar procesos lógicos. Estado terminal conceptual `processing_failed` para el intento fallido.

`original_cleanup_status` y `azure_result_cleanup_status` son ejes independientes del proceso, con intento/confirmación/error; no presentar una solicitud de borrado como destrucción física verificada. `match/difference/insufficient` son resultados de comparación temporal; los badges por campo **Respaldado / Con diferencia / Sin respaldo** se derivan según §9 y no cambian evaluaciones previas.

## 8. Contratos de OCR y parsers

Especificación de responsabilidades; ningún contrato se implementa en esta fase.

**Puerto OCR propuesto:** `OcrClient.submit(AuthorizedDocumentReference) -> OcrOperation`; `get_result(OcrOperation) -> UntrustedOcrResult`; `request_result_deletion(OcrOperation) -> DeletionOutcome`. Implementación seleccionada: Azure Document Intelligence. El nombre de la interfaz puede cambiar; proveedor y frontera de responsabilidades están aprobados.

- `AuthorizedDocumentReference`: objeto propio reservado, referencia temporal segura, tamaño/formato disponibles y correlación opaca. No contiene bytes/base64 ni URL arbitraria elegida por cliente; no se registra su credencial temporal.
- `OcrOperation`: ID remoto, versión/modelo utilizados, generación, estado y fechas para reanudación/idempotencia. Persistir localizador mínimo sólo mientras haga falta consultar/borrar; no un resultado OCR completo.
- `UntrustedOcrResult`: reconocimiento de texto/layout y páginas/advertencias devueltas. Aplicar límite de tamaño de respuesta y validación de envoltura antes del parser; el JSON/texto de Azure no demuestra autenticidad ni corrección financiera. No pedir salidas binarias adicionales ni figuras/renderizados innecesarios.
- `DeletionOutcome`: distingue solicitado/aceptado/error/no soportado; no afirmar eliminación física inmediata al recibir un acuse.

**Puerto de interpretación:** `DocumentParser.parse(OcrRecognition, ParseContext) -> CandidateExtraction`, con parsers específicos `PayslipParser`, `SavingsStatementParser`, `EmploymentDocumentParser` (nombres orientativos). Azure hace OCR, estos parsers hacen interpretación financiera local determinista sobre texto/layout, **no sobre PDF/imágenes**. Versión/API/modelo y allowlists quedan fijados en §§2 y 17: v4.0, `2024-11-30`, `prebuilt-layout`; no SDK ni modelos personalizados.

`ParseContext` aporta un tipo seleccionado, su allowlist explícita aprobada, referencia temporal, idioma y versión; no une campos de todos los tipos. `CandidateExtraction` contiene sólo candidatos permitidos, unidad/período/semántica cuando necesarios, referencia de página y advertencias enumeradas. No se envía declaración previa al OCR ni se usa para hacer que el parser encuentre una coincidencia deseada.

Secuencia obligatoria: **resultado Azure -> parser por tipo documental -> Pydantic -> normalización -> comparación -> revisión del usuario**. Pydantic estricto (`extra=forbid`, números finitos, rechazo de booleanos como importes, listas/strings acotados, enums y campos allowlist). Validación semántica independiente: unidad/período/cobertura; JSON válido o confidence alto no convierte un candidato en dato aceptable. Semántica cerrada: ingreso = renta líquida mensual; ahorro = monto disponible identificable. Sólo las cuatro claves de la allowlist §2 según su parser; bruto, imponible, haberes y sueldo base nunca sustituyen renta líquida.

Múltiples candidatos sin regla determinista suficiente o OCR ambiguo producen `ambiguous/not_detected` y advertencia para revisión; no sumar, promediar, escoger máximo, asumir cero ni elegir por confidence. Si el usuario declara una corrección manual, se distingue de extracción respaldada; el detalle de UX sigue sujeto a revisión. Fuera de allowlist se descarta/rechaza, sin escribir al perfil. El OCR puede reconocer incidentalmente texto de la página completa; eso **no habilita** interpretarlo o conservarlo como otro antecedente financiero: la extracción de dominio y la persistencia permanecen acotadas al tipo seleccionado (E1).

Azure **no decide qué valor es correcto, no actualiza antecedentes, no escribe Supabase, no calcula score ni asigna estados de respaldo**. Parsers/normalización/comparación no tienen escritura ni scoring. El servicio HU23 sólo modifica antecedentes financieros tras confirmación; metadata y candidatos temporales mínimos pueden persistirse antes para orquestación/revisión. No se envían originales, texto OCR o candidatos a Groq/OpenAI/otro LLM. `backend/app/ai.py` sigue fuera de este flujo documental.

## 9. Comparación y confirmación

Comparación determinística por campo entre declaración vigente y candidato semánticamente compatible. Para texto/categorías: normalizar espacios, Unicode y mayúsculas/minúsculas, mapear sólo sinónimos controlados a enums existentes y comparar igualdad; no fuzzy matching ni similitud del LLM como criterio de respaldo. No alterar identificadores ni negar diferencias por remover palabras. La política exacta de equivalencias se aprueba/versiona. Para importes CLP usar precisión decimal y política inicial de igualdad exacta; redondeo/tolerancias sólo tras acuerdo versionado. Mostrar diferencia absoluta y signo cuando comparable. No convertir UF/USD usando valores externos ni usar fórmulas de scoring. Si falta unidad/período o evidencia inequívoca de la semántica aprobada del campo, resultado `insufficient`; `ingreso_mensual` es renta líquida mensual, sin sustituirla por bruto/imponible.

Múltiples ingresos, cuotas, empleadores, saldos o documentos contradictorios producen candidatos separados y advertencia; nunca «último gana», promedio automático ni suma asumida. Alcance inicial recomendado: un documento por sesión; documentos adicionales son sesiones separadas. La comparación conserva referencia de revisión; otra sesión confirmada o una actualización rápida obliga a releer y revisar antes de confirmar.

La transacción de confirmación bloquea perfil/plan HU13 y sesión en orden fijo, valida propietario/rol/base/TTL/generación, compara revisión HU13 y revisión de sesión/extracción, resuelve idempotencia, registra decisiones, persiste únicamente candidatos elegidos en un evento `data_update` de HU13 **sin evaluación asociada**, y agenda limpieza atómicamente (§11). No llama al camino actual de `TrackingService.execute` que calcula, ni `/score`, proyecciones con scoring o IA explicativa. Una confirmación de coincidencias sin cambiar valores registra evidencia y cierra documento sin crear evaluación ni modificar datos financieros.

Mismo request y contenido devuelve la misma decisión; otro contenido con la misma clave da 409. Confirmar y cancelar compiten: una sola transición terminal tiene éxito. Dos confirmaciones de sesiones distintas sobre la misma base no se fusionan automáticamente. Si la base cambió, 409 y nueva comparación/revisión explícita. Los errores de infraestructura antes del commit permiten reintentar; después del commit consultar estado evita repetir decisiones.

### Semántica propuesta de los tres estados (E4)

- **Respaldado:** evidencia comparable revisada y confirmada que sostiene el valor de la versión consultada, dentro de cobertura/vigencia acordadas. Aplica tanto a coincidencia confirmada como a una diferencia cuyo candidato se acepta: la comparación original fue «diferencia», pero el nuevo declarado coincide con la evidencia. Conservar ese resultado original sólo como categoría de trazabilidad.
- **Con diferencia:** el usuario finalizó la revisión y conserva un declarado distinto del candidato comparable; hay discrepancia pendiente para ese campo/versión. No exponer el valor rechazado al ejecutivo. Una diferencia sólo detectada en una sesión abierta no publica automáticamente una alerta comercial.
- **Sin respaldo:** no hay evidencia confirmada aplicable a ese campo/versión, es insuficiente/no comparable, no llegó a existir una confirmación aplicable o el dato cambió posteriormente. Un intento cancelado/fallido/expirado no sobrescribe el estado anterior ni invalida un respaldo ya existente; `processing_failed` es del intento, no un `sin_respaldo` permanente del antecedente. Acompañar motivo neutro cuando ayude; no afirmar ausencia de deuda/ingreso por ausencia de extracción.

La existencia de PDF no basta para respaldar un dato; tampoco el confidence del modelo. Vincular por campo/valor y referencia de evento/versionado. Un cambio posterior del valor o vencimiento acordado deja sin respaldo vigente hasta nueva revisión; no modifica decisiones ni evaluaciones anteriores. Un evento de otro campo no invalida necesariamente todos los respaldos: conservar los que todavía correspondan al mismo valor/cobertura. No introducir expiraciones documentales arbitrarias por tipo: v1 conserva fecha/cobertura y vinculación al valor/versión; una ampliación de vigencias será política posterior, no bloqueo para implementar lo aprobado ni plazo inferido de E3.

## 10. Estrategia de borrado y expiración

**Decisiones aprobadas:** original temporal en Storage; iniciar eliminación al confirmar, cancelar, error terminal o abandono; **máximo de retención por abandono: 24 horas**. Cleanup idempotente con reintentos. La eliminación del original no se pospone hasta actualizar el score. El criterio oficial E3 no fija horas; el techo de 24 h es el contrato técnico aprobado en esta conversación.

**Cleanup periódico CERRADO / APROBADO:** endpoint backend protegido + ejecución programada, reutilizando el patrón existente de RutaHogar: `backend/app/lead_changes/routes.py::require_cron` valida bearer/secreto y `vercel.json` ya declara `/lead-changes/daily-digest`. Añadir la operación HU23 siguiendo ese patrón al implementar, sin infraestructura extra exclusiva, sin modificar ahora esos archivos y sin reutilizar el trabajo comercial como tarea de borrado.

Frecuencia inicial: **cada 1 hora**. La limpieza periódica recupera abandonos, `delete_pending`, errores temporales y `expires_at` vencidos; no sustituye el intento inmediato en confirmación/cancelación/error terminal. `expires_at` se fija desde la reserva con margen que contemple intervalo horario, retraso de ejecución y presupuesto acotado de reintentos **antes de `created_at + 24 h`**. No usar expiración a las 24 h y sumar después otra hora de cron. Ajustar el margen concreto durante implementación; nunca renovar retención por polling/retry.

Seguro ante concurrencia: reclamar lotes con exclusión/lease o bloqueo transaccional, revalidar sesión/objeto y usar borrado idempotente; ejecuciones solapadas no duplican decisiones ni marcan éxito antes de verificar ausencia. Registrar intentos/próximo intento/resultado y recuperar leases vencidos. Horario exacto, lotes y presupuesto de retries son detalles no bloqueantes, con pruebas de reloj y fallos que demuestren el techo; la limitación real de una caída prolongada sigue siendo observable, no una garantía inventada del cron.

### Original Supabase y temporales de RutaHogar

- Guardar cierre y obligación de borrado en la misma transacción de confirmación/cancelación/error. Intento inmediato vía Storage API; reintentos idempotentes con estado durable, causa acotada y próxima ejecución. «No encontrado» es éxito para un objeto reservado conocido; otros errores no se convierten en eliminado.
- Usar [Storage API para borrar](https://supabase.com/docs/guides/storage/management/delete-objects), no eliminar sólo filas `storage.objects`, que dejaría el binario huérfano. Verificar ausencia antes de marcar `deleted_at`.
- Reconciliar uploads sin finalize, reservas huérfanas, cargas iniciadas antes del cierre y completadas tarde, reanudaciones y ausencia previa del archivo. No reutilizar rutas ni borrar el localizador hasta cerrar la ventana de cargas tardías/verificar ausencia.
- Purgar payload de revisión, candidatos rechazados y referencias temporales al cerrar; conservar únicamente datos declarados aceptados y evidencia mínima. Vercel nunca genera archivos temporales binarios, rasterizados o thumbnails en este diseño. Eliminar buffers de reconocimiento de la aplicación tras parsear; no almacenarlos en DB/colas/logs/analítica ni navegador. Colas/estado contienen IDs, no texto OCR.
- Un fallo de borrado no deshace una actualización ya confirmada ni crea una evaluación. La UI informa «antecedentes confirmados; eliminación pendiente», sin afirmar borrado exitoso. La recuperación usa el endpoint protegido programado y estado reintentable aprobado en P4; detalles de alerta se fijan al implementar.

### Resultado remoto Azure: ciclo de vida independiente

Después de obtener el reconocimiento y persistir **sólo los candidatos/metadatos necesarios para revisión**, solicitar eliminación anticipada del resultado remoto cuando la combinación API/modelo lo permita. No esperar a confirmar ni depender exclusivamente de retención automática. La API v4 documenta `Delete Analyze Result`, que marca el resultado para eliminación; ese acuse no demuestra por sí solo destrucción física inmediata. Esta operación corresponde a la API **`2024-11-30`** elegida; solicitarla para el resultado `prebuilt-layout` obtenido, sin confundir acuse con destrucción física inmediata. [Operación oficial de borrado](https://learn.microsoft.com/en-us/rest/api/aiservices/document-models/delete-analyze-result?view=rest-aiservices-v4.0+(2024-11-30)).

Conservar el ID/localizador remoto mínimo y estado de limpieza mientras sea necesario; eliminarlo/minimizarlo al concluir. No guardar endpoint real, credenciales ni signed URL en evidencia. Si falla parser/validación, cancelar/expirar o llegar un resultado después del cierre, también registrar/intentar borrado remoto cuando esté disponible. No reenviar el documento para poder borrar un resultado anterior.

Si sólo existe operación pendiente al cancelar, impedir aplicación de resultados y mantener seguimiento mínimo para limpiar el resultado cuando termine. No asumir soporte de cancelación remota. Si el borrado no está disponible/falla, registrar esa limitación y aplicar reintentos acotados de cleanup; nunca confundir «original Supabase eliminado» con «resultado Azure eliminado». La retención automática del proveedor es una salvaguarda adicional, no el único mecanismo de RutaHogar.

El techo de 24 h de abandono rige el original Supabase y no demuestra un plazo físico de eliminación de copias Microsoft. Documentar ambos ciclos y la transferencia temporal al usuario. Antes de uso real validar política del recurso/API, backups, retención y evidencia de eliminación sin inventar garantías. La configuración finita de retención de metadata mínima es un detalle no bloqueante a concretar al implementar, sin OCR bruto ni nuevos datos; valores aceptados como declaración tienen el ciclo HU13, distinto del documento.

Validar que la infraestructura de limpieza puede cumplir el techo aprobado; alertar por retrasos y frenar nuevas cargas si se pierde capacidad de limpieza. Una caída prolongada puede impedir borrado físico: el diseño debe mostrar la falla y resolverla, sin ampliar el plazo ni afirmar garantía por tener sólo un cron.

## 11. Integración con evaluaciones existentes

### Problema confirmado y evidencia de una solución menor

`TrackingService.execute()` calcula un resultado en `if not target_event_id: evaluation = evaluate(...)`, sin distinguir `data_update` de `evaluation`. También resuelve datos de mercado antes de esa decisión. Las correcciones que cambian estado generan otra evaluación. Por tanto, enviar hoy un `data_update` a `/tracking/events` tras confirmar documentos produciría un cálculo no solicitado. El problema es el acoplamiento en la orquestación, no una limitación del modelo de eventos ni permiso para sobrescribir una evaluación.

Se verificó que `tracking_events.evaluation_id` admite NULL; `lineage.append_event()`/`reconstruct()` admiten `data_update` sin resultado; `TrackingService.read()` distingue `latest_effective_snapshot` de `current_evaluation` y busca hacia atrás la última evaluación real. `hu13_commit()` itera las evaluaciones recibidas, por lo que admite `evaluations=[]` sobre un plan existente. Estos puntos permiten reutilizar la declaración vigente en vez de introducir otro perfil financiero. La comprobación es por inspección; faltan las pruebas integradas y de consumidores antes de implementar esta opción.

### Decisión aprobada de separación y mecanismo técnico propuesto

1. Mantener candidatos en el payload temporal documental hasta la decisión E2. Ningún candidato sin confirmar entra en HU13.
2. Incorporar una **vía interna específica de actualización documental sin cálculo**, por ejemplo `append_confirmed_document_update`. Reutilizar validación de snapshot, linaje y commit HU13, evitando la rama actual de `execute`, el resolver de mercado y todo scorer. No cambiar globalmente el significado operativo de `data_update` para formularios/hitos existentes ni exponer un flag de cálculo controlado por el navegador.
3. En confirmación con diferencias aceptadas, crear exactamente un evento `data_update` con patch de valores elegidos, snapshot completo validado, `evaluation_id=NULL`, `evaluations=[]` y provenance mínima de decisión/versión. Usar timestamp de servidor y revisión esperada. Confirmar coincidencias o conservar todos los declarados no requiere evento financiero si no cambió ningún dato; sí registra evidencia/decisión.
4. La decisión, el evento financiero y la obligación de borrar deben comprometerse **en una sola transacción**. Proponer RPC `hu23_confirm_document` que llame internamente a `hu13_commit` con registros construidos por backend y añada decisión/limpieza en la misma transacción. No encadenar dos llamadas REST y suponer atomicidad. Puede bastar añadir esta RPC sin cambiar la firma ni el SQL de `hu13_commit`; verificar constraints/triggers finales en tests locales. Bloquear perfil/plan/sesión en orden único.
5. Al confirmar, la declaración vigente cambia; el score, clasificación y UUID de la última evaluación **no cambian**. UI: «Antecedentes actualizados; última precalificación realizada el…». No llamar automáticamente `/score`, `/tracking/projection` ni refresh que dispare scoring como efecto del cierre documental.
6. La acción **«Actualizar score con datos validados»** usa `latest_effective_snapshot`, no con el input antiguo de la última evaluación. Sólo esa acción explícita y su revisión/envío del snapshot usan el comando HU13 `evaluation` existente y crea otra evaluación/historial. El backend resuelve referencias documentales pertinentes a los valores efectivamente evaluados; no confía en provenance del cliente. No hay borrador aparte que consumir.

**Por qué es menor que el borrador separado:** conserva una sola fuente de declaraciones, reutiliza revisión/locks/linaje y deja el flujo actual de scoring como camino explícito. Evita tabla `declared_financial_drafts`, overlay, invalidación cruzada, dos versiones financieras paralelas y un endpoint adicional de evaluación. No basta eliminar una línea del cálculo: hay que separar también la resolución de mercado y verificar atomicidad y consumidores.

**Alternativas consideradas:** (a) cambiar todos los `data_update` para que nunca calculen: semánticamente posible, pero cambia comportamiento de hitos/otros flujos y excede el ajuste acotado recomendado; (b) conservar patch aceptado en una tabla de borrador independiente: aísla HU13, pero añade persistencia y sincronización; queda como **propuesta alternativa no aprobada**, sólo a reconsiderar si las pruebas demuestran que el camino HU13 sin cálculo rompe invariantes que no pueden aislarse razonablemente; (c) confirmar y recalcular inmediatamente: descartada por las instrucciones de esta sesión.

### Consistencia, consumidores y datos históricos

Los consumidores que hoy suponen «última declaración = input de última evaluación» deben leer por separado declaración vigente y resultado histórico. Revisar prefill de `ScoreForm`, actualización rápida/hitos y vistas de perfil/ejecutivo para que no vuelvan a aplicar inputs viejos. La revisión HU13 debe corresponder al snapshot que el usuario realmente revisó, no obtenerse justo antes de enviar un formulario antiguo. Un cambio concurrente exige releer y confirmar; no sobrescribir automáticamente campos de otro evento. Las proyecciones que invocan scorer no forman parte de la respuesta de confirmación; un cálculo referencial existente en otra pantalla no es una nueva evaluación persistida y no debe presentarse como resultado documental.

La confirmación sí puede actualizar progreso de metas basadas en datos declarados al volver a consultar ese seguimiento; esto no equivale a recalcular un score ni reescribir el plan baseline. Verificar series/eventos sin evaluación, avisos de metas, triggers y cualquier automatismo comercial para que nunca anuncien mejora de precalificación por el mero respaldo.

Si sólo hay evaluación legacy y falta plan HU13, no dejar que `execute()` cree baseline evaluando implícitamente. Recomendación a validar: adopción explícita del baseline desde la evaluación ya existente, preservando su UUID/input/result y declarando origen legacy, sin nueva puntuación ni provenance retrospectiva inventada. Después puede añadirse el evento documental sin cálculo. Si faltan antecedentes completos, la revisión documental muestra lo no comparable y la adopción/nueva evaluación se resuelve explícitamente; no introducir el borrador separado como obligación general por este caso excepcional.

No añadir archivos, texto bruto ni candidatos rechazados a `evaluations.financial_data`, `scoring_history.snapshot`, `tracking_events.recorded_complete_snapshot` ni anotaciones. Los valores **aceptados** sí son declaración financiera y pueden conservarse bajo el ciclo HU13; las referencias de respaldo son mínimas. Una evaluación anterior conserva su input/result/provenance y no recibe etiquetas retroactivas. Toda vista debe identificar si muestra respaldo de declaración vigente o evidencia de una evaluación concreta; cargar evidencia hoy no acredita lo que estaba respaldado al calcular hace meses.

No modificar `scoring.py`, `scoring_engine` ni umbrales para premiar documentos o castigar diferencias. La vía específica HU23 sin scoring, la acción explícita posterior y no cambiar HU13 globalmente están aprobadas. Los nombres de funciones, RPC y detalles de atomicidad son propuestas pendientes de implementación/pruebas; no se ejecutan cambios remotos.

- **Autorización equivalente segura:** subida autenticada oficial de Supabase (upload con JWT vigente y upsert:false) más lease revocable de **10 minutos**, reservado por backend para una única ruta. Se evaluó createSignedUploadUrl, pero su token tiene vigencia fija de [dos horas](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl). La autorización por RLS permite cierre/cancelación efectiva sin entregar esa capacidad duradera al navegador. No se emite un nuevo token ni se expone Service Role.
- Ruta **user_id/process_id/uuid.ext** creada exclusivamente en servidor, ligada al proceso y con extensión validada. No se acepta ruta, owner ni tamaño autoritativo del cliente; tampoco se conserva filename original. El navegador envía un Blob sin nombre original directamente a Storage, nunca al backend.
- RLS de inserción exacta usa el [helper oficial de operación](https://supabase.com/docs/guides/storage/schema/helper-functions) storage.allow_only_operation('object.upload'), para impedir convertir el lease en un signed upload de dos horas. Policies **restrictivas** aíslan HU23 incluso ante otra policy permisiva amplia. Nadie del cliente, incluido propietario y ejecutivo, puede SELECT/listar/descargar/UPDATE/DELETE originales. Service Role conserva lifecycle.
- Requisito de compatibilidad: el motor Storage debe soportar ese helper y la operación oficial object.upload. La migración falla cerrada si falta el helper; no instala una simulación en producción ni degrada permisos. El bootstrap de tests únicamente reproduce sus primitivas para PostgreSQL local. Su disponibilidad real y la transferencia binaria completa deberán comprobarse en un entorno autorizado antes de habilitar uso; T2 no consulta ni modifica Supabase remoto.
- Nueva tabla interna **document_uploads**, una fila por proceso y FK compuesta proceso/owner: bucket/ruta, extensión/MIME, páginas declaradas cliente, lease/fechas de reconciliación, id/tamaño del objeto admitido y código acotado de fallo. Sin grants del navegador, OCR, filename, URLs ni tokens. El path permanece como **localizador operativo de recuperación**, aunque document_processes.storage_path se anule al confirmar borrado; no es evidencia financiera. T8 debe purgar esta fila tras cierre, borrado verificado y fin de la ventana de reconciliación, conservando sólo evidencia mínima de T1.
- **GET /tracking/documents/config** expone restricciones desde configuración backend y tipos soportados. **POST /tracking/documents/sessions/{id}/upload** recibe revisión/extensión/MIME/páginas cliente y devuelve bucket/ruta/expiración/restricciones. **POST .../{id}/upload/complete** sólo recibe revisión. Autenticación y owner provienen del servidor; no hay endpoint público de OCR ni lectura de originales.
- Finalize consulta **metadata de storage.objects mediante RPC privilegiada**, bajo los mismos locks que el lifecycle: objeto existente, bucket/ruta/owner exactos, sesión/lease vigentes, tamaño positivo ≤4 MB y MIME autorizado. No descarga binarios. Una admisión válida pasa a ready; un fallo cierra el intento como processing_failed, sin datos/evidencias/evaluaciones nuevas, y deja obligación de borrado. Repetir finalize en ready es idempotente. Tampoco se permite al servicio interno saltar a ready/processing sin objeto admitido.
- Un trigger revalida owner/ruta/lease/estado al insertar metadata, incluso cuando Storage escribe privilegiadamente después de transferir bytes, y bloquea reemplazos de contenido/identidad. Otro impide acusar eliminación mientras exista metadata del objeto. Son defensas ante commits tardíos/concurrencia; el borrado físico se solicita siempre por **Storage API**, nunca eliminando filas de storage.objects en código de producción.
- Reintento sin objeto y proceso abierto: misma identidad/formato, lease reutilizado mientras vigente o renovado tras vencer, sin extender expires_at. Objeto ya existente: finalizar/verificar; no sobrescribir. Un objeto inválido o finalize fallido cierra ese intento y se inicia otro proceso con nueva identidad. No se acumulan varios objetos activos por proceso.
- Cancelar/confirmar o detectar fallo/expiración conserva primero el cierre lógico y delete_pending; luego intenta borrado inmediato por API privilegiada. Fallos físicos dejan retry_required, sin revertir el cierre. ### Aclaración del pendiente de score

El pendiente representa una diferencia financiera aceptada explícitamente y aún no incorporada en los datos de entrada de la evaluación vigente. Una confirmación coincidente o una diferencia conservada como declarada no crea pendiente por sí sola. El estado se deriva del historial y la evidencia persistidos, sobrevive a una nueva sesión y sólo se consume al registrar una evaluación que incorpore el valor vigente. Confirmar un documento no calcula score.
